# Preparation and launch review

14 November 2026; delegated reviewer `prefix_reviewer_b`. Read complete `prepare_assets.py`, `job_supervisor.py` and `build_transport.py` locally. No remote connection, download or model execution performed by this reviewer.

Preparation is acceptable to launch on the user-confirmed free runtime. Downloads use the exact pinned public revision and `token=False`, with implicit token use disabled and HF cache located under the new task results directory. It checks available disk before weight downloads, validates architecture, layer count, hidden size, lack of quantization and template hash, and hashes every materialized snapshot file. Downloading weights is distinct from loading them or running inference; the script performs neither. Manifest inventory includes the index, four referenced shards and requested tokenizer/config assets. A post-preparation comparison with previously frozen same-revision weight/config hashes would provide additional independent provenance.

The six-file upload is explicit and contains no pairing file or secrets. Existing remote files must match bytes; differing content is not overwritten. The durable launch records an exclusive intent before detached subprocess creation, redirects stdout/stderr to a persistent log, saves PID and refuses a second launch when intent or exit evidence exists. A crash between intent and PID therefore blocks for inspection, rather than duplicate work. Supervisor persists child exit status and traceback. Worker lock/attempt ledger provides the separate prompt-level duplicate guard.

One local preservation issue was reported to the parent: upload mode writes `UPLOAD_MANIFEST.json` unconditionally before checking whether an existing transport script differs. A later changed upload could overwrite old manifest evidence and then fail the transport guard. Use exclusive-or-identical manifest persistence. This does not block the first preparation launch with already verified immutable uploaded bytes, but must be corrected before rebuilding a changed upload manifest.

Remote preparation writes only new task cache/preparation files, while upload writes only the approved new code/input paths. Supervisor expects job directory creation by the durable launcher, which the generated cell provides. There is no model call or hidden paid-resource activation in these scripts. Hardware model loading, dtype/device residency and runtime hidden-state fidelity remain separate subsequent checks.
